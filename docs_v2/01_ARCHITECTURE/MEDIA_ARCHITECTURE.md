# MEDIA ARCHITECTURE

## Purpose
Define the media management architecture for ATLS, focusing on operational evidence and domain-linked media as core business data. This document establishes the rules for media ownership, storage, upload lifecycles, offline handling, tenant isolation, and AI-safe constraints.

## Scope
Covers media as operational evidence, domain-linked architecture, storage strategy, cloud integration, offline capture, upload queues, compression, thumbnails, streaming, CDN, access control, lifecycle cleanup, observability, and mobile-first behavior.

## 1. Media Philosophy
ATLS treats media as operational evidence and domain-linked business data. Media is not generic attachments but core evidence for agricultural operations, including harvest photos, equipment inspections, inspection reports, and compliance documentation. Media must always be linked to a specific domain entity and never exist as orphaned files.

## 2. Media as Operational Evidence
Media serves as verifiable evidence for business processes: harvest yields with photos, equipment maintenance with videos, inspection reports with PDFs, and compliance audits with audio recordings. Each media item must include metadata linking it to the operational context, timestamps, and user identity.

## 3. Media Ownership Rules
Media ownership is domain-driven: each media item belongs to a specific entity (e.g., harvest record, equipment item, inspection task). Ownership is enforced through database relationships, not file system paths. Media cannot be created without a parent entity, and deletion cascades from the domain entity.

## 4. Domain-Linked Media Architecture
Media is architected as an extension of domain aggregates: harvest aggregates include media references, equipment aggregates link to inspection media, and reports include embedded evidence. Media references are stored in PostgreSQL with foreign keys, while binaries reside in object storage.

## 5. Media Storage Strategy
Media binaries are stored in cloud object storage (e.g., S3-compatible), never in PostgreSQL or local file systems. Storage paths include tenant prefixes for isolation. Metadata, references, and access controls are persisted in the database, with binaries accessed via pre-signed URLs.

## 6. Cloud Storage Architecture
Use scalable object storage with multi-region replication for durability. Storage buckets are partitioned by tenant and white-label variant. Implement lifecycle policies for automatic cleanup and cost optimization. Support for large files through multipart uploads and resumable transfers.

## 7. Object Storage Philosophy
Object storage is the single source of truth for media binaries. It provides high availability, scalability, and integration with CDNs. Avoid local file storage or database BLOBs. Use storage classes for cost-effective retention of operational evidence.

## 8. Pre-Signed Upload Flow
All uploads use pre-signed URLs generated by the backend. The frontend requests a pre-signed URL from the API, then uploads directly to object storage. This offloads upload traffic from the backend and ensures secure, authenticated access without exposing storage credentials.

## 9. Upload Lifecycle
Upload lifecycle: request pre-signed URL → upload binary to storage → persist metadata in database → link to domain entity → generate thumbnails asynchronously → invalidate caches. Failures trigger rollback of metadata and cleanup of partial uploads.

## 10. Chunk Upload Strategy
Large media (videos, high-res images) use chunked uploads with resumable sessions. Chunks are uploaded in parallel or sequentially, with progress tracking and retry logic. Incomplete uploads are resumable after network interruptions or app restarts.

## 11. Large Video Upload Rules
Videos are compressed client-side before upload. Use adaptive bitrate encoding for mobile. Chunk uploads with MD5 checksums for integrity. Background processing handles transcoding after upload completion. Limit concurrent video uploads to preserve bandwidth.

## 12. Offline Media Capture
Offline media capture stores files locally in secure, tenant-isolated storage (e.g., IndexedDB or mobile file system). Captured media is queued for upload once connectivity returns. Metadata is persisted locally to link media to domain entities.

## 13. Offline Media Queue
Offline media queue is separate from operational mutation queues. It prioritizes critical evidence uploads while deferring non-urgent media. Queue items include media metadata, domain links, and retry state. Sync progress is observable and recoverable.

## 14. Media Compression Rules
Compress media client-side to reduce upload size and storage costs. Use lossy compression for images/videos where quality allows, lossless for PDFs/reports. Compression settings are configurable per media type and use case (e.g., inspection photos vs. marketing images).

## 15. Thumbnail Generation Strategy
Thumbnails are generated asynchronously after upload using server-side processing. Store thumbnails in the same object storage bucket with predictable paths. Use WebP or optimized formats for web delivery. Generate multiple sizes for different UI contexts.

## 16. Media Metadata Persistence
Media metadata is stored in PostgreSQL with fields for: domain entity ID, media type, size, checksum, upload timestamp, user ID, tenant ID, and custom tags. Metadata is versioned and auditable. Binaries are referenced by storage keys, not embedded.

## 17. Media Reference Rules
Media references use storage keys and pre-signed URLs for access. References are embedded in domain entities and API responses. Avoid exposing direct storage URLs; always proxy through pre-signed mechanisms. References include expiration and access scopes.

## 18. Tenant Isolation Rules
Tenant isolation is enforced at storage paths (e.g., /tenant-{id}/media/), database schemas, and CDN distributions. Media from one tenant cannot be accessed by another. Isolation extends to offline queues, local storage, and sync processes.

## 19. White-Label Isolation Rules
White-label variants have separate storage prefixes and CDN configurations. Media branding (e.g., watermarks) is applied during processing. Isolation prevents cross-brand media leakage and ensures compliance with brand-specific retention policies.

## 20. Media Access Control
Access control is role-based and tenant-scoped. Users can only view media linked to entities they have permission to access. Pre-signed URLs include embedded permissions and expiration. Audit logs track media access for compliance.

## 21. Permission-Based Media Visibility
Media visibility is determined by domain permissions: harvest media visible to farm operators, inspection media to auditors. UI components filter media based on user roles. Public media is forbidden; all media requires authentication.

## 22. Media Streaming Rules
Streaming is supported for videos and audio using CDN-backed delivery. Use adaptive streaming protocols (e.g., HLS) for mobile. Streaming URLs are pre-signed and time-limited. Cache streaming manifests for performance.

## 23. CDN Integration Strategy
Integrate with global CDNs for low-latency media delivery. CDN caches are invalidated after uploads or metadata changes. Use CDN for thumbnails, streaming, and public-facing media. Tenant-specific CDN distributions ensure isolation.

## 24. Media Caching Rules
Cache media at CDN and browser levels with appropriate TTLs. Invalidate caches on media updates or deletions. Use cache keys that include tenant and version identifiers. Avoid caching sensitive operational evidence indefinitely.

## 25. Media Expiration & Retention
Retention policies are domain-specific: harvest evidence retained for seasons, inspection media for compliance periods. Automatic expiration triggers cleanup of binaries and metadata. Retention is configurable per tenant and white-label.

## 26. Orphan Media Cleanup
Orphan media (unlinked to domain entities) is detected and cleaned up periodically. Use background jobs to scan for orphaned binaries and remove them. Prevent orphan creation through strict ownership rules.

## 27. Media Observability
Observe upload success rates, queue depths, storage usage, and access patterns. Use telemetry for media processing times, failure rates, and bandwidth consumption. Surface observability in admin dashboards with tenant isolation.

## 28. Media Failure Recovery
Implement retry logic for failed uploads with exponential backoff. Recover partial uploads through resumable chunks. Provide user feedback for recoverable failures. Log failures for analysis and prevent data loss.

## 29. Background Processing Strategy
Background workers handle compression, transcoding, thumbnail generation, and virus scanning. Use queue-based processing (e.g., Redis or SQS) to decouple from user requests. Process media asynchronously to avoid blocking UI.

## 30. Async Transcoding Rules
Transcode videos and audio asynchronously after upload. Use cloud functions or dedicated workers. Generate multiple formats (e.g., MP4, WebM) for compatibility. Transcoding is batched and prioritized based on media importance.

## 31. Virus & Security Scanning
Scan all uploaded media for viruses and malware using integrated security services. Quarantine suspicious files and notify administrators. Scanning is performed before metadata persistence and thumbnail generation.

## 32. Mobile Upload Constraints
Optimize uploads for mobile: compress aggressively, use chunking for large files, respect battery and data limits. Pause uploads on weak signals. Provide progress indicators and resumable state.

## 33. Weak Network Upload Strategy
On weak networks, prioritize metadata uploads over binaries. Use smaller chunks and longer timeouts. Allow users to defer large uploads. Resume automatically when connectivity improves.

## 34. Media Search & Filtering
Search media by metadata tags, domain links, timestamps, and user associations. Filter by type, size, and status. Search is tenant-scoped and permission-aware. Use database indexes for efficient queries.

## 35. Media Timeline Rendering
Render media in chronological timelines for operational workflows (e.g., harvest progress, inspection history). Embed media previews in timelines with lazy loading. Support zooming and filtering within timelines.

## 36. Agricultural Evidence Workflows
Workflows integrate media capture: inspectors attach photos to reports, harvesters record videos of yields, equipment operators upload maintenance evidence. Workflows enforce required media types and validation.

## 37. AI Safety Rules
AI must not:
- store media blobs in Zustand or global state
- embed base64 media in database fields
- process videos synchronously in UI threads
- generate unbounded thumbnails without limits
- upload directly to public buckets
- bypass pre-signed URL flows
- store media in PostgreSQL BLOBs

## 38. Forbidden Media Anti-Patterns
- global unlinked media buckets
- storing binaries in PostgreSQL
- direct backend memory uploads
- synchronous processing of large media
- public tenant-shared storage
- base64 encoding in APIs
- unbounded thumbnail generation

## 39. Real-World Agricultural Media Scenarios
- **Harvest evidence:** farmers capture yield photos offline, upload in batches after returning to signal, with thumbnails generated for quick review.
- **Equipment inspection:** technicians record videos of maintenance, compress for mobile upload, and link to equipment records with audit trails.
- **Compliance audit:** auditors attach PDFs and audio notes to inspection reports, stored tenant-isolated with retention policies.
- **Remote monitoring:** sensors upload images of crop health, processed asynchronously for AI analysis, cached via CDN for dashboard access.

## 40. Future Media Evolution Strategy
- Advance AI-driven media analysis for crop health and yield prediction.
- Implement advanced compression and streaming for 4K videos.
- Expand offline media capabilities with peer-to-peer sync.
- Integrate blockchain for immutable evidence chains.
- Enhance mobile capture with AR overlays and automated tagging.
- Evolve CDN strategies for edge computing and real-time processing.
